# Автотесты для UI Stellar Burgers

Проект содержит автоматизированные UI‑тесты для веб‑приложения [Stellar Burgers](https://stellarburgers.education-services.ru/).  
Тесты написаны на Python с использованием Selenium, pytest, Allure и паттерна Page Object.

---

## Что проверяется

### Основная функциональность

- переход по клику на «Конструктор»;
- переход по клику на раздел «Лента заказов»;
- при клике на ингредиент открывается модальное окно с деталями;
- модальное окно ингредиента закрывается по крестику;
- при добавлении булки в заказ счётчик этого ингредиента увеличивается на 2 (верх и низ булки).

### Раздел «Лента заказов»

- при создании нового заказа счётчик «Выполнено за всё время» увеличивается;
- при создании нового заказа счётчик «Выполнено за сегодня» увеличивается (в стабильном окружении);
- после оформления заказа номер заказа появляется в разделе «В работе» (в стабильном окружении).

Для части проверок, которые нестабильно работают именно в Firefox (особенности обновления UI и модального окна), в тестах добавлены пометки `xfail`, чтобы зафиксировать эти проблемы как ожидаемые для данного браузера, а не как дефекты тестов.

## Паттерн Page Object

Для упрощения поддержки тестов используется паттерн **Page Object**.

### BasePage

Общий базовый класс со стандартными действиями:

- `open(url)` — открыть страницу;
- `click(locator)` — клик с явным ожиданием кликабельности;
- `find(locator)` — поиск одного видимого элемента;
- `find_all(locator)` / `finds(locator)` — поиск всех видимых элементов;
- `get_text(locator)` — получение текста элемента.

### MainPage

Описывает главную страницу приложения:

- навигация:
  - переход в «Конструктор»;
  - переход в «Лента заказов»;
- работа с ингредиентами:
  - открытие модалки первого ингредиента;
  - drag‑and‑drop ингредиента в конструктор;
  - получение значения счётчика ингредиента;
- работа с заказом:
  - получение суммы заказа;
  - клик по кнопке «Оформить заказ»;
  - ожидание появления номера заказа в модальном окне (с обработкой заглушки `9999`);
- работа с модалками:
  - закрытие модалки ингредиента и заказа по крестику;
  - ожидание скрытия оверлея модалки;
- авторизация через UI (при необходимости).

Для повышения стабильности учтены особенности модального окна: перед кликами по вкладкам и ингредиентам используется ожидание исчезновения оверлея и небольшие ретраи кликов, если они перехватываются.

### OrdersFeedPage

Описывает раздел «Лента заказов»:

- проверка видимости ленты;
- получение числа «Выполнено за всё время»;
- получение числа «Выполнено за сегодня»;
- получение списка номеров заказов в разделе «В работе»:
  - ожидание появления реальных номеров (отсев заглушек вроде «Все текущие заказы готовы!»);
  - нормализация номеров (обрезка ведущих нулей).

Пример использования Page Object в тесте:

```python
main = MainPage(driver)
main.open_main()
main.drag_first_ingredient_to_constructor()
main.drag_first_ingredient_to_constructor()
main.click_order_button()
order_number = main.wait_for_order_modal()
main.close_modal()

main.go_to_feed()
feed = OrdersFeedPage(driver)
total = feed.get_total_done()
```

## Авторизация через API

Для ускорения тестов, где не проверяется форма логина, используется фикстура `authorized_driver`:

- выполняется запрос `POST /api/auth/login` с тестовыми учётными данными;
- из ответа берутся `accessToken` и `refreshToken`;
- токены записываются в `localStorage` браузера через `execute_script`;
- после обновления страницы тесты запускаются уже в авторизованной сессии.

Это позволяет:

- не дублировать шаги UI‑логина в каждом тесте;
- сократить время прогона;
- сосредоточиться на проверке бизнес‑логики конструктора и ленты заказов.

## Поддерживаемые браузеры и нестабильность Firefox

Фикстура `driver` параметризована по браузерам:

```python
@pytest.fixture(params=["chrome", "firefox"])
def driver(request):
    ...
```

Каждый UI‑тест выполняется:

- в **Chrome** — основном и стабильном браузере;
- в **Firefox** — для проверки кросс‑браузерности.

Выявленные особенности Firefox:

- оверлей модального окна иногда дольше закрывается и перекрывает клики по ингредиентам;
- в модальном окне заказа может отображаться временный номер `9999`, в то время как в ленте заказов уже виден реальный номер;
- счётчик «Выполнено за сегодня» и счётчик ингредиента могут обновляться с задержкой.

Для таких сценариев в тестах добавлены пометки `xfail` **только для Firefox**, чтобы:

- прогон оставался зелёным для Chrome;
- в Allure‑отчёте явно фиксировались ожидаемо нестабильные кейсы для Firefox.

## Требования

- Python 3.11+
- Google Chrome и Mozilla Firefox
- Java (для генерации Allure Report)
- Allure Commandline

### Установка Java (Windows)

1. Скачать JDK (например, JDK 26) с официального сайта Oracle или Adoptium.
2. Установить JDK.
3. Настроить переменные среды:
   - `JAVA_HOME` = `C:\Program Files\Java\jdk-26.0.1`
   - добавить `C:\Program Files\Java\jdk-26.0.1\bin` в `PATH`.
4. Проверить:

   ```bash
   java -version
   ```

### Установка Allure

1. Установить Allure (например, через `scoop install allure` или вручную).
2. Проверить:

   ```bash
   allure --version
   ```

## Запуск тестов

1. Активировать виртуальное окружение:

   ```powershell
   .\venv\Scripts\Activate.ps1
   ```

2. Запустить все тесты в Chrome и Firefox:

   ```powershell
   pytest -v
   ```

   Благодаря параметризации фикстуры `driver` каждый тест выполнится в двух браузерах.

3. Запустить тесты с генерацией результатов для Allure:

   ```powershell
   pytest -v --alluredir=allure-results
   ```

4. Открыть Allure‑отчёт:

   ```powershell
   allure serve allure-results
   ```

В отчёте будут видны:

- статусы тестов (PASSED/FAILED/XFAILED) отдельно для Chrome и Firefox;
- шаги выполнения (из `@allure.step` в Page Object);
- набор диаграмм и тенденций (trends, status chart).

## Чистый прогон и отчёт

Чтобы получить отчёт только по свежему прогону:

```powershell
Remove-Item -Recurse -Force .\allure-results
pytest -v --alluredir=allure-results
allure serve allure-results
```
